# PlayDrop for iPhone

The iOS app of PlayDrop (Phase 4 in `PLAN.md`). It is a sender plus a foreground receiver:

- **Send**: share anything to PlayDrop from Photos, Files or any app. The share extension
  copies the items into a queue in the App Group container and hands off to the app, which
  sends them with the Rust core. The extension never hosts the core and never listens.
- **Receive while open**: while PlayDrop is on screen the app runs the core, listens on
  port 42187 and receives files, clipboard text and pings like any other PlayDrop device.
- **Outbox pull**: computers and Android phones keep an outbox for the iPhone. When you open
  the app it pulls everything queued for it, so files sent while the phone was asleep arrive
  as soon as you open PlayDrop.
- **No background listening.** iOS suspends the app in the background and its sockets die.
  The app tells the other side it is asleep and stops the core; there is no
  `UIBackgroundModes` entry and no always-on claim anywhere (PLAN.md anti-pattern 11).
- **Find my phone, while open.** When a paired device rings this iPhone, PlayDrop plays a
  system sound with a haptic every 2 s for up to 60 s and shows "<device> is looking for
  this iPhone" with a Stop button. iOS gives apps no way to override the silent switch or
  ring from the background, so this only works while PlayDrop is on screen (with the
  silent switch on, only the haptic is felt); going to the background stops it.

The core starts only once onboarding is done: starting it makes iOS ask for Local Network
access, and that question must come after the onboarding page that explains it.

| Path | What it is |

## Building on a Mac

You need a Mac with Apple silicon, Xcode 16 or later, Homebrew and an Apple Developer
account (a free account can run on your own phone for 7 days, but cannot get the App Group
or multicast entitlements reliably; use a paid team).

1. Install the tools:
   ```sh
   brew install xcodegen          # project.yml was generated with XcodeGen 2.46.0
   curl https://sh.rustup.rs -sSf | sh
   xcode-select -s /Applications/Xcode.app
   ```
2. Build the Rust core and the Swift bindings (from `apps/ios`):
   ```sh
   scripts/build-core.sh               # release, device and simulator slices
   scripts/build-core.sh --sim-only    # quicker inner loop, simulator only
   scripts/build-core.sh --debug       # debug Rust build (slow transfers, never ship it)
   ```
   Run it again after every change under `crates/`. It prints the library sizes at the end.
   It also repairs the generated C header: uniffi-bindgen 0.32.2 writes two callback fields
   as `` `open` `` (Swift's keyword escaping leaking into C), which clang rejects. The script
   strips the backticks outside comments and stops if any remain; re-check this on every
   UniFFI upgrade and drop the step once the header comes out clean.
3. Set up signing:
   ```sh
   cp Local.xcconfig.example Local.xcconfig
   ```
   and put your 10-character Team ID in `DEVELOPMENT_TEAM`. Keep `CODE_SIGN_STYLE =
   Automatic` unless you manage profiles yourself. This must happen before step 4, because
   XcodeGen refuses a missing config file.
4. Generate and open the project:
   ```sh
   xcodegen generate
   open PlayDrop.xcodeproj
   ```
5. Pick the `PlayDrop` scheme and a real iPhone, and run. Local Network access is asked for
   right after the onboarding pages, not at launch; allow it.
6. Run the unit tests with Product > Test (Cmd-U); a simulator is fine for them. They are
   hosted by the app, link nothing twice (the packages are dependencies with `link: false`)
   and clean up the Keychain items and defaults suites they create.

If the build stops at "Check the Rust core is built", step 2 has not run. If Xcode instead
complains while resolving packages that `PlayDropCoreFFI.xcframework` is missing, it is the
same cause: Swift Package Manager checks the binary target before any build script runs.

**Use a real device.** The simulator shares the Mac's network stack: it never shows the
Local Network prompt, does not enforce the multicast entitlement, and its discovery results
say nothing about a phone. Use it for layout only.

Bundle IDs are `org.playdrop.ios` and `org.playdrop.ios.share`. If another team already
registered them, change them in `project.yml` and in
`Packages/PlayDropShared/Sources/PlayDropShared/Identifiers.swift` together (and the App
Group and keychain group in both entitlements files).

## Multicast entitlement

The core finds devices with its own mDNS responder (`_playdrop._tcp`) and a UDP multicast
beacon on `239.255.42.187:42187`. iOS lets an app send or join multicast only with the
`com.apple.developer.networking.multicast` entitlement, which Apple grants on request:

1. Sign in as the team's Account Holder or an Admin and open
   https://developer.apple.com/contact/request/networking-multicast
2. Give the bundle ID `org.playdrop.ios` and explain the use in plain words, for example:
   "PlayDrop is an open-source app that sends files between the user's own devices on the
   local network. It finds the user's paired computers and phones with its own mDNS
   responder for `_playdrop._tcp` and a small signed UDP beacon to 239.255.42.187 with TTL 1.
   No data leaves the local network."
3. When Apple approves it (days to weeks), open Certificates, Identifiers & Profiles, select
   the App ID `org.playdrop.ios`, enable Multicast Networking under Additional Capabilities,
   and let Xcode refresh the profile (automatic signing does it on the next build).

Until then the profile does not carry the entitlement and signing fails. Remove the
`com.apple.developer.networking.multicast` key from `PlayDrop/Resources/PlayDrop.entitlements`
for local builds (do not commit that change). Without it:

- discovery fails: no device appears by itself, and Settings > Diagnostics (`diagnose()`)
  lists the multicast join failures and the mDNS error;
- pairing still works by typing the computer's address and by scanning its QR code;
- paired devices still reconnect by their last-known address.

## Export compliance

`Info.plist` sets `ITSAppUsesNonExemptEncryption` to `false`. Our reading: the only
cryptography is standard TLS 1.3 (rustls) protecting the app's own connections, plus
sealing its own key at rest, which falls under the standard-protocol and mass-market
exemptions, so App Store Connect asks no further questions. **Check this reading before the
first submission** (Apple's "Complying with Encryption Export Regulations" page and, if in
doubt, the US BIS rules for 5D992). Distribution in France may need its own declaration.

## App icon

`PlayDrop/Resources/Assets.xcassets/AppIcon.appiconset` has the single 1024 x 1024 slot
but no image yet. Builds run with a blank icon; App Store upload is refused until a
1024 x 1024 PNG without transparency is added to that slot.

## Phase 4 gates (manual checklist)

Run on a real iPhone on the same Wi-Fi as a Linux machine. The Linux side runs the daemon
as in the root `CLAUDE.md` (`/tmp/pd-a`, receive folder `/tmp/pd-a-in`). Shorthand used
below:

```sh
bus() { busctl --user call org.playdrop.PlayDrop.Daemon1 /org/playdrop/PlayDrop/Daemon1 \
        org.playdrop.PlayDrop.Daemon1 "$@"; }
bus Request s '{"op":"peers"}'          # find the iPhone's Short ID
```

Pair first: in the app open Add device and scan the QR from the desktop window, or type the
computer's address. Both screens show the same Short IDs and code.

- [ ] **A camera-roll dump to Linux works.** In Photos select 200 or more photos and videos,
  Share > PlayDrop. On Linux count what arrived and compare with the number selected:
  ```sh
  find /tmp/pd-a-in -type f -newer /tmp/pd-mark | wc -l   # touch /tmp/pd-mark before sending
  ```
- [ ] **A 2 GiB video goes through the share extension handoff.** Make the file on Linux,
  put it on the phone through the outbox (next gates), then share it back from the Files
  app with Share > PlayDrop. The hashes must match:
  ```sh
  head -c 2G /dev/urandom > /tmp/big-2g.mov && sha256sum /tmp/big-2g.mov
  # after it comes back:
  sha256sum /tmp/pd-a-in/big-2g*.mov
  ```
  The extension must not be killed (it streams to disk); the app sends after the handoff.
- [ ] **Receives while open.** With PlayDrop on screen, send a 400 MiB file from Linux.
  `SendFiles` takes file descriptors, never paths (SR-26):
  ```sh
  head -c 400M /dev/urandom > /tmp/f400.bin && sha256sum /tmp/f400.bin
  bus SendFiles sah <iphone-short-id> 1 3 3</tmp/f400.bin
  ```
  On the phone open Files > On My iPhone > PlayDrop, long-press the file, and compare the
  size; for a hash, share it back to Linux and run `sha256sum` on the received copy.
- [ ] **Pulls queued files on open.** Close PlayDrop (swipe it away or lock the phone).
  Queue a file for the iPhone, then open the app; it must arrive without any tap:
  ```sh
  bus QueueOutboxFiles sah <iphone-short-id> 1 3 3</tmp/f400.bin
  bus Request s '{"op":"outbox"}'                 # the item is listed until it is pulled
  ```
  After opening the app, `{"op":"outbox"}` is empty and the file is in Files > PlayDrop.
  The same flow from a second CLI host (Android stand-in, see root `CLAUDE.md`):
  `outbox <iphone-short-id> /tmp/f400.bin`, then `outbox` to list; the phone pulls on open
  (`pull <peer>` is the CLI's own puller side, for comparison).
- [ ] **Denied Local Network permission shows the fix screen.** Settings > Privacy &
  Security > Local Network > PlayDrop off, then open the app. It must show the fix-it screen
  that explains the switch and opens Settings, not an empty device list.
- [ ] **App Store copy is accurate.** Read `AppStore/copy.md` against the app as built:
  receives only while open, queued items arrive on open, no background listening, no
  account, local network only, GPL-3.0-or-later.

## Continuous integration

`.github/workflows/ios.yml` runs on GitHub's free macOS runners for every push that touches
`apps/ios` or the FFI crate: it builds the Rust core for the simulator, generates the project
with XcodeGen, compiles the app and the extension unsigned, and runs `PlayDropTests` on an
iPhone simulator. Logs and the `.xcresult` bundle are uploaded as the `ios-build-logs`
artifact. A green run proves the code compiles and the unit tests pass; it proves nothing
about Local Network, multicast, signing or the gates above, which need a real iPhone.

## What Linux verified

There is no Xcode on the development machine, so these were checked on Linux
(`scripts/check-linux.sh`, `--list` shows exactly what it looks at):

- every Swift file parses with `swiftc -parse`;
- `scripts/typecheck-linux.sh` generates the real Swift bindings from a host build of
  `playdrop-ffi`, applies the same header repair as `build-core.sh` (so clang accepts the
  header), and compiles against them, in Swift 5 mode with complete strict concurrency:
  every app file that does not import SwiftUI (50 of 79: Core, Share, Outbox, Clipboard,
  Notifications, Intents and the plain-logic UI files), the extension's non-SwiftUI files,
  and the unit tests. Apple frameworks are stubs with Apple's labels
  (`scripts/linux-typecheck/modules`); the SwiftUI files are then checked by a script for
  names, argument labels and private members they use from the compiled code. Not covered:
  SwiftUI, PhotosUI, QuickLook and AVFoundation API use, and the Objective-C runtime part of
  `AppOpener`;
- `Packages/PlayDropShared` builds and its tests pass (`swift test`);
- `playdrop-ffi` is clippy-clean for `aarch64-apple-ios` and `aarch64-apple-ios-sim`, and
  `cargo rustc --crate-type staticlib` produces the simulator `.a` (with stub `cc` and `ar`,
  so nothing is linked);
- the Swift bindings generate with the expected file names (`PlayDropCore.swift`,
  `PlayDropCoreFFI.h`, `PlayDropCoreFFI.modulemap`);
- every plist, entitlements file and privacy manifest parses, the catalogs are valid JSON,
  and `project.yml` is valid YAML;
- XcodeGen 2.46.0, built from source on Linux, generates `PlayDrop.xcodeproj` from
  `project.yml` (and refuses to without `Local.xcconfig`, as described above). The
  generated project has the extension in the PlugIns embed phase, the three resources in
  Copy Bundle Resources, both local packages linked as listed, and the pre-build check.

Not verified yet: opening the project in Xcode, the build and link, signing, running the
unit tests, the share extension on a device, and every gate above.

## Known risks for the first Mac build

What the Linux checks cannot rule out, collected from the Phase 4 work. Look here first
when the first Xcode build or device run misbehaves.

- **QR screen capture protection** (`UI/AddDevice/SecureContainer.swift`) hosts the QR code
  in the private canvas subview of a secure `UITextField`. It depends on an undocumented
  view layout; if a later iOS changes it, the container falls back to showing the code
  normally. Check that a screenshot of the QR screen comes out blank.
- **Opening the app from the share extension** (`PlayDropShare/AppOpener.swift`) uses the
  responder-chain `openURL` workaround through the Objective-C runtime, because extensions
  have no supported call. Apple has broken it before; "Done" plus opening PlayDrop by hand
  always works.
- **Delegate isolation**: `NotificationDelegate` and the QR scanner's
  `AVCaptureMetadataOutputObjectsDelegate` use `nonisolated` methods (and
  `@preconcurrency import AVFoundation`). Xcode 16's SDK annotations may still warn; fix by
  adjusting the annotations, not by turning strict concurrency off.
- **Photos picker**: `PhotosPicker(..., preferredItemEncoding: .current)` and
  `FileRepresentation(importedContentType:importing:)` were written from the documentation
  only (the stub models their labels). Check that a 4K video arrives as a file, not in memory.
- **`@Bindable var settings = settings`** as a local inside `SettingsView.body` (iOS 17
  pattern for an `@Environment` observable) has not been compiled.
- **`.quickLookPreview($preview)`** on the Transfers tab has not been compiled or run.
- **`#if DEBUG`** in `CoreHostImpl` relies on `SWIFT_ACTIVE_COMPILATION_CONDITIONS: DEBUG`
  for the Debug configuration (set in `project.yml`); without it debug builds log at info.
- **Device name**: `UIDevice.current.name` returns the generic model name ("iPhone") on
  iOS 16 and later without the `com.apple.developer.device-information.user-assigned-device-name`
  entitlement, so peers see "iPhone" until the user sets a name in Settings.
- **Multicast entitlement**: signing fails until Apple grants it (see above).
- **App icon**: missing; builds work, App Store upload does not (see above).
- **XCFramework module map in a subfolder** (`Headers/PlayDropCoreFFI/module.modulemap`):
  chosen so it does not collide with other binary packages; if `import PlayDropCoreFFI`
  fails, check that Xcode found it there. The same applies to the unit tests, which reach
  the packages through `link: false` dependencies: if they report a missing
  `PlayDropCoreFFI` module, put the XCFramework's headers on the test target's search path
  rather than linking the packages a second time (two copies of the same types in one
  process make `as?` casts across them fail).
- **Export compliance**: `ITSAppUsesNonExemptEncryption = false` is our reading of the
  rules; check it before the first submission (see above).
